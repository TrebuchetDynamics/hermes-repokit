# Hermes RepoKit team runtime

Date: 2026-09-27. **Status: implementation plan accepted in principle with pre-code refinements; this revision records the requested lifecycle/recovery contract. No code or live operations have started.**

The user approved the architectural direction, including self-hosting as a release gate. This document makes that direction concrete while retaining the decisions below for explicit review. It supersedes the permanently default-only/Holographic/six-command/one-total-container direction in the [historical spec](2026-09-26-hermes-repo-installer-design.md) and [historical plan](../plans/2026-09-26-hermes-repo-installer.md). Old Task 1 is paused; no implementation code, tests or implementation commits happened. Existing documentation history is not an implementation milestone.

## 1. Review decisions first

**Approved direction:** product `Hermes RepoKit`, CLI `hermes-repokit`; one Hermes runtime and one RepoKit Compose project per canonical repository; fresh SAFE installation with native default only, deliberately expanded to five native profiles by Managed Mode; native Kanban orchestration; native OpenViking memory; internal Laya sidecar; advisory Nerve plugin; pinned native Superpowers; safe/managed/fleet modes; host-controlled self-apply. No Docker socket in Hermes.

**Not yet authorized:** installing/building/running this stack, downloading models, reading credentials, submitting private content, spending inference budget, contacting channels, production deployment, or executing a replacement plan. The plan is accepted in principle subject to the requested pre-code refinements recorded here; review the revised lifecycle and recovery contract before the first code task. Runtime/provider/download authority remains separate.

### Owner decisions and authority

- **Privacy contract:** preserve the no-raw-data requirement. The inspected native provider cannot satisfy it for ordinary memory-connected sessions. An additional native upload-opt-out enhancement needs owner scope approval; broad transcript consent would change the privacy contract and is neither presumed nor recommended. Nonsecret fixtures need their own bounded permission.
- **Private operating authority:** authorize providers, permitted data, retention/egress, download/compute scope and budgets through private setup before the affected operation. Deployment selections and exact-revision scanner caution findings retain explicit owner approval; research pins are not deployment approval.
- **Product compromises, if proposed:** any reduction in requested autonomous operation or protected-state guarantees needs an explicit owner decision. For example, replacing autonomous reviewer test execution with host-operated evidence handoff is not a silent engineering fallback. No compromise is selected here.

### Engineering obligations, not an owner questionnaire

Engineers select and demonstrate the supported execution/runner mechanism within the approved topology, loaded completion policy and failure behavior, input/run fencing, secret permissions across mount aliases, pin-aware Laya packaging, immutable candidate artifacts, resource bounds, supported hosts and denial/recovery fixtures. These are implementation and qualification work, not five decisions the owner must solve before planning. No runner, artifact or native enhancement is claimed implemented by this spec. The development checkout has been renamed to `/home/xel/git/hermes-repokit` before any runtime identity, fixture or package is created; this is not automatic relocation/adoption support for installed repositories. Pi/subagents are development conveniences only: installation, runtime, user tests, generated configuration and self-hosting must have no Pi package, executable, service, credential or resource dependency.

### Operation gates and release acceptance

| Unresolved condition | Operation withheld | Independent work that may proceed within its own authority |
| --- | --- | --- |
| Native upload conflicts with the privacy contract | Incompatible memory-connected sessions and private-data processing; no provider switch or invented toggle to evade it. | Offline investigation, eligible infrastructure provisioning and non-inference health/status without starting uploading sessions. |
| Role, execution, protected-path or review guarantees are unqualified | Affected execution tools/autonomous implementation dispatch; reviewer remains inspection-only until its test surface qualifies. | Independent provisioning, observation, read-only tools and qualification fixtures that do not exercise the unsupported path. |
| Model/data/download/compute authority absent | The corresponding download, inference, ingestion or disclosure. | Non-inference infrastructure/status and advisory Nerve observation without Laya calls. |
| Candidate component artifact/support unqualified | Deployment or use of that unsupported component/path. | Engineering qualification and independent components with their own satisfied gates. |

Full release readiness still requires the complete qualified stack and real self-hosting acceptance in §11; partial component availability is not that milestone. Written-spec approval permits replacement planning with explicit engineering dependencies and operation gates, not an obligatory five-part owner interview. Actual privacy/authority/compromise decisions must precede the affected scope or operation. Proposed budgets and envelopes below are design contracts, not upstream defaults or measured capacity.

## 3. Native profile fleet and effective capabilities

Fresh `install` initializes only native root `default`, Kanban and admitted non-autonomous supporting components in SAFE mode. It must not create specialist profile directories or clone a specialist roster. `setup` configures default and may stage independently selected specialist model/auth material through protected private I/O, without creating native specialist homes or starting sessions. `activate` starts only eligible components and does not expand the roster. The first explicit `mode managed` transaction provisions native `researcher`, `planner`, `builder`, `reviewer` alongside existing `default`, with explicit descriptions and independently selected private model/auth configuration; it releases claims only after the full readiness/review/budget gates pass. Provisioning itself runs with dispatch suspended, including across restart. Partial creation is recorded truthfully, retry is idempotent and preserves configured profiles/credentials, and provisioning failure before release leaves no new claims. A crash after the native release effect may leave real runs; recovery suspends further claims and reconciles their provenance, never asserts fictitious zero work. A later `mode safe` retains provisioned profiles and all their state: default-only describes a fresh installation, not destructive downgrade behavior. `mode fleet` requires an admitted engineering roster established through Managed Mode; it cannot bypass first-time team admission. Do not clone credentials from a user's profile. Root default home is not `profiles/default`. Shared memory identity is deliberately provisioned; credentials are not copied by inference.

| Profile | Description/work product | Capability contract |
| --- | --- | --- |
| default | Coordinates goals, shared decisions, useful DAGs, assignments and handoffs via Kanban. | Read/coordination/memory; no implementation tools or source writes. Not a dispatched builder. |
| researcher | Reads repository and authorized external sources; returns evidence with immutable citations. | Read/search/research/memory; no source writes or arbitrary execution. |
| planner | Turns accepted evidence into a bounded plan and explicit interfaces/acceptance. | Read/memory/structured plan handoff; no source writes. Store plan evidence in native card context or approved non-source artifact path. |
| builder | Implements only approved card scope, with tests and evidence, then requests same-card review. | Scoped write/execution/test/memory capabilities through the qualified surfaces below; cannot approve its own completion or host lifecycle. |
| reviewer | Independently inspects diff, provenance and acceptance; approves or requests changes on the same card. | Read/evidence/memory by default, no implementation writes. Tests only through a qualified scoped execution surface; never an unrestricted shell described as read-only. |

At the inspected Hermes revision, use supported effective toolsets (`platform_toolsets.cli`, `agent.disabled_toolsets`, resolved worker `--toolsets`) and native policy hooks/custom toolset support, not SOUL text alone. Worker Kanban lifecycle tools are automatically appended despite profile toolset selection; merely omitting `kanban` or hiding `kanban_complete` in desired YAML does not prevent completion. Qualified narrow deny-toolsets can participate in later subtraction, but a verified loaded pre-tool policy and actual worker-schema checks remain mandatory. `file` contains writes; `safe` is not read-only; individual tool names must not be mistaken for toolset selectors. A read subset needs qualified packaging and a pre-tool policy, including plugin/MCP/browser surfaces. Verify actual exposed schemas and execution-time veto for every profile/session/worker. Resolution failure must block dispatch rather than silently omit the pin.

**Bounded v1 trust model:** trust the host operator/administrator, selected runtime and admitted plugin/tool implementations as the enforcement base. Do not trust model output, repository text or test code to obey role policy. The supported model-facing surface is the resolved tool schema, policy-mediated native Kanban calls and explicitly exposed scoped execution tools. Direct administrative CLI/DB access and installing arbitrary plugins are not worker capabilities. V1 does not claim comprehensive resistance to a compromised runtime/plugin, hostile same-UID process outside those surfaces or kernel escapes; stronger adversarial isolation needs separate scope. This exclusion does not make an exposed credential path safe or excuse bypasses through a supported execution tool.

Concrete supported-surface guarantees to implement and test:

- Default/researcher/planner receive no implementation-capable tool schema; execution-time policy denies disallowed tools and protected paths, including plugin/MCP/browser surfaces actually enabled. Missing policy/tool resolution fails closed for the affected worker.
- Builder writes are restricted to approved source scope. Reviewer can inspect and request bounded tests but cannot implement source changes or self-review builder work. Tests execute repository code: a command-name allowlist, clean cwd or worktree alone cannot make them read-only.
- Each exposed execution tool must document its input snapshot/worktree, writable outputs, credential/runtime-path access, process/network authority and resource bounds. Qualification must show builder execution cannot change native review state, selectors/manifests/credentials or invoke host lifecycle; reviewer tests cannot alter the reviewed source or protected state. Tests may write disposable scratch/output, and evidence is bound to the exact candidate. Denial fixtures cover these concrete surfaces and both `.hermes` aliases, not an open-ended proof against every hostile same-UID program.
- Engineers choose the runner/isolation mechanism that meets those guarantees on supported hosts within the one-Hermes topology. A narrow snapshot-bound test tool is a candidate, not a mandated new in-container sandbox architecture. No extra Hermes, privileged workaround or Docker socket is authorized. If a mechanism cannot meet a concrete guarantee, withhold that execution surface and affected autonomous dispatch while independent work continues. Host-operated isolated test evidence is a possible owner-approved autonomy compromise, not default completion of the reviewer requirement.

## 4. Kanban authority, workflow and review gate

Initialize native Kanban with `orchestrator_profile: default`, `dispatch_in_gateway:false`, `auto_decompose:false`; authorize only provisioned worker profiles. Safe mode suppresses dispatch even if cards are ready. Native selectors, descriptions, board resolution and explicit concurrency controls must be qualified against the selected Hermes version. Automatic decomposition remains off in every mode; default intentionally designs the DAG. `goal_mode` is excluded from the default reviewed implementation path: do not expose or enable a goal lifecycle as a review/dispatch bypass. Any future goal-mode integration requires independent lifecycle and same-card-review qualification.

Golden flows are **builder → reviewer**, **researcher → builder → reviewer**, and **architecture research → planner → builder → reviewer**. Research/planning cards exist only when useful. Every dependent sibling card receives shared schemas/interfaces/protocol assumptions, relevant evidence, scope and acceptance; sibling conversations are not shared context. OpenViking recall is helpful context, not a substitute for the card contract.

For a change-bearing card: builder submits evidence and `kanban_request_review`; assigned reviewer claims that same card (native review → running), evaluates independently, then uses `kanban_request_changes` to return it to the recorded implementer or authorized `kanban_complete` to finish. Revision/re-review stays on the same card. Related research/planning cards may be dependencies; they do not manufacture separate review cards or a second lifecycle.

**Required RepoKit policy/verification gate, not an existing native guarantee:**

- Builder cannot complete its own change-bearing card. Trusted native provenance must identify the implementing run's profile as exactly `builder` and the approving run's profile as exactly `reviewer`; both runs must exist, their run IDs must differ, and the actor identities must differ. These are acceptance checks, not prompt instructions. Completion also requires recorded builder handoff, acceptance evidence and review of the exact candidate revision/evidence fingerprint. New changes invalidate old approval.
- Profile tool exposure plus a mandatory loaded native `pre_tool_call` policy must reject unauthorized completion/review/assignment actions and stale/wrong-run evidence before a native transition. Default cannot approve on the reviewer's behalf. The current reviewer-owned run must have been claimed from review, with a matching latest handoff and no superseding changes. Classify change-bearing cards outside worker-editable prose. Native provenance/history remains the record; RepoKit does not directly rewrite the DB or invent a parallel approved/done state machine.
- Qualify the supported model-tool and scoped execution paths defined in §3: no worker tool may bypass review through native CLI/Python/SQLite, policy mutation or an exposed connector. Verify loaded policy before the affected worker release, fail-closed supported mutation calls, current-run fencing and stable reviewed inputs. Native outer hook-dispatch errors can continue execution and prechecks are not atomic with a DB transition; engineers must address those failure/race cases for the supported path or withhold that path. This is ordinary model-tool enforcement, not a universal database invariant against administrators or arbitrary hostile same-UID callers. An upstream transactional guard is an engineering option where needed, not a blanket prerequisite for unrelated work; post-hoc Nerve reporting never substitutes for prevention.
- Native `complete_task` currently permits more states than the intended review flow and does not universally enforce reviewer independence. Release tests must demonstrate rejected self-completion, wrong reviewer/run, stale review and omitted evidence, as well as a successful changes/re-review cycle.
- Nerve may report missing evidence/review cycles. It never acts as the gate's lifecycle executor. Authorized native actors perform transitions; owner intervention is explicit and audited, never Nerve auto-blocking.

Golden user path: **install → setup → activate → mode managed → status**. This is the eventual README path, not a command sequence authorized in this design phase.

- **Safe:** fresh install has only native default, dispatch disabled, `auto_decompose=false`, Nerve observational. After team provisioning, SAFE retains the roster/history without dispatch. OpenViking enabled and Laya available are the intended qualified product state, not a license for raw uploads/downloads during bootstrap. Independent authorized infrastructure/observation can proceed. Sidecar degradation may allow already-authorized native work to continue under §9, without pretending the full stack is ready.

## 6. Native OpenViking memory and privacy boundary

Use only Hermes's native external provider: `memory.provider: openviking`; `memory.openviking.endpoint: http://openviking:1933`, account `repokit`, user `repo_id`, optional agent/peer unset. Provision `server.auth_mode: api_key`; root/admin authority must remain outside worker authority, and supply a project-bound ordinary user key through approved profile secret configuration (`OPENVIKING_API_KEY`, not YAML). **Protection gap:** all of `.hermes` is mounted in Hermes. A root/bootstrap key in `.hermes/openviking/ov.conf` or another child file may be visible through `/opt/data` and `/workspace/.hermes`; giving the client a user key does not prove it lacks root-key access. Engineers must verify per-service ownership/permissions and supported tool/execution restrictions at the actual UIDs/mount aliases. If a worker surface exposes root secrets or protected writes, withhold that surface and affected dispatch rather than claim protection. This does not block independent nonsecret provisioning/observation; any proposed reduction in protected-state guarantees needs owner approval. No new secret infrastructure is silently added. Effective precedence is environment → linked ovcli → YAML → defaults. Confirm every profile resolves the intended endpoint/key/user and no peer override; equal namespace strings alone prove neither sharing nor authorization.

Per-repository service, mount, private network and credentials are essential: server account-level resource/agent scopes may be shared even though user memory paths differ. Positive shared-profile recall and negative cross-repo access tests are release requirements. The official OpenViking image must be pinned/qualified; disable its bundled bot with `OPENVIKING_WITH_BOT=0` or supported `--without-bot`. Use local AGFS/vector backends at the reviewed source contract; do not accidentally provision another gateway or storage topology.

Working-method policy: recall before substantive work and submit durable lessons afterward; skip trivial work. Useful lessons include decisions, conventions, debugging discoveries, verified APIs, recurring failures, preferences and rejected approaches. Avoid submitting raw logs/statuses/diffs/secrets/ephemeral output as deliberate knowledge. **This policy cannot prevent native raw session upload.** Native `viking_remember` requests extraction; completion/indexing/recall are separate observations, not a guaranteed exact insertion.

The privacy conflict is unavoidable: automatic turn/tool synchronization can include private data and secrets before durable-memory extraction. No exposed Hermes opt-out was verified. Server extraction-disable archives without extracting and does not solve disclosure. Automatic sync is background lifecycle work outside ordinary tool dispatch; hiding memory tools does not stop it. The recommended compatible native solution is an upload opt-out, including session switches/end commits, pending-session recovery and unintended built-in mirroring paths, while preserving deliberate native memory operations. That feature is absent at the research pin: additional enhancement scope needs owner approval, while engineers investigate and qualify the native mechanism. It is not a local invented setting. Until resolved, incompatible memory-connected sessions/private-data processing are blocked; separately authorized service provisioning, non-inference checks and offline research can proceed without starting such sessions or silently selecting another provider. Existing raw sessions require a distinct retention/remediation decision, never automatic deletion. Private setup must separately authorize permitted data, local/remote processing, retention, provider costs and revocation behavior; broad raw-session consent would require an explicit change to the privacy requirement. Do not present the original durable-only requirement as satisfied. No second memory provider, interception/filter pipeline or invented toggle is authorized here.

Optional curated resource ingestion is separately opt-in: `README*`, `AGENTS.md`, `CONTRIBUTING*`, `docs/**`, `adr/**`, `architecture/**`, `specs/**`, respecting Git ignore, file-size limits and link/ownership checks. Exclude `.env*`, keys/credentials, `.git`, `.hermes`, dependencies, generated/build output and dumps; never index the whole source tree automatically. These are intended admission rules, not an already-enforced property of native `viking_add_resource`; keep automatic ingestion disabled until qualified. Allowed documents can contain secrets. Native resource upload is snapshot-based; no implied watch, repo mount or automatic resource recall (`recall_resources` defaults false).

Keep native built-in memory enabled (`memory.memory_enabled`, `memory.user_profile_enabled`) and expose permitted memory tools. Built-in stores are profile-local under `memories/`; they coexist rather than replicate OpenViking. On outage retain provider selection and remote data, surface empty/unavailable external recall and uncertain unsent writes. Do not promise shared recall, lossless turn replay, extraction success or automatic backfill. Pending-session recovery must be reported separately from delivery guarantees.

## 7. Nerve advisory event pipeline

`repokit-nerve` uses native plugin `register(ctx)`, hooks and tool registration. Its proposed tools are `nerve_assess(task_id)`, `nerve_status(task_id)`, `nerve_explain(task_id)`, `nerve_history(task_id)`. Status/explain/history read derived evidence; assess requests bounded asynchronous assessment and returns pending/known/unknown, never waits under a Kanban hook or takes lifecycle authority.

Verified hooks at the research Hermes revision:

| Hook | Important payload/timing qualification |
| --- | --- |
| `kanban_task_claimed` | Task/run/profile/board/assignee; post-commit, typically dispatcher with dispatch lock held. |
| `on_kanban_worker_spawned` | Adds worker PID/workspace; dispatch lock held. |
| `kanban_task_completed` | Adds summary; completion caller process after commit. |
| `kanban_task_blocked` | Adds reason; blocking caller process after commit. |
| `on_kanban_worker_exited` | PID/exit kind/code/outcome/retry status; dead-PID reclamation, not every normal exit. |
| `on_kanban_worker_stale_claim` | PID/heartbeat-stale/retry status; expired-claim reclamation, not every heartbeat. |
| `on_kanban_task_updated` | Changed field names, not full values; supported non-lifecycle mutations. |
| `on_kanban_dispatch_tick` | Board/profile/dry-run/outcome/DispatchResult, no task-common payload; after lock release. |

Common task `profile_name` is the executing profile, not necessarily assignee. Native telemetry version is `hermes.observer.v1`; callbacks tolerate additive kwargs. These synchronous callbacks have no protective timeout. They must do only bounded whitelist projection and nonblocking handoff, with no SQLite contention wait, disk fsync loop, network, model call, memory recall or subprocess startup in the hook.

**Proposed v1 pipeline:** multiple dispatcher/worker/mutator producers → bounded local IPC ingress → one supervised background consumer inside Hermes → bounded event spool and derived SQLite state → bounded Laya client. Plugin producers load in every relevant process. Consumer ownership uses a single-instance lease/lock and restart fencing, not a thread started independently by every worker. Exact transport/supervision packaging is a future slice interface decision; it must demonstrate nonblocking sends with bounded payloads and no unbounded fallback. An absent/full consumer drops or coalesces observations and marks coverage degraded; it must never delay native dispatch to save telemetry. Event-loss diagnostics themselves must not block the hook.

Proposed initial limits for review: 4 KiB normalized hook envelope, 256 queued ingress events, 16 MiB rotating spool, 10,000 assessment records or 7 days retention (whichever first). Include producer instance/sequence, event/schema IDs, repo/board/task/run identity and observed time; deduplicate received IDs and coalesce superseded task/run observations. Treat durability as best-effort and delivery as potentially duplicated, missing or reordered, not exactly-once. Restarts resume bounded work, discard stale results and never cause catch-up model storms. Bounds must be configuration-validated and tested; these numbers are not upstream guarantees.

Read-only reconciliation is mandatory because request-review/request-changes events are absent from these hook fire sites, exits/heartbeats are incomplete and producers can fail. Read canonical native events/cards through a version-qualified, nonmutating, WAL-aware observer; no ordinary DB connect/init, dispatch dry-run, direct writes or copied board DB. Track a bounded checkpoint and detect gaps/retention/schema drift. Unavailable or incomplete evidence yields unknown coverage, not invented review cycles. Reconciliation may restore derived evidence, never replay transitions or infer missing budget/iteration values as zero. Do not promise that a historical timestamp proves a worker is live.

Derived state contains task/run/profile, observed start/elapsed/heartbeat age, available budget/iteration counters, failure fingerprints/repeated blockers, review cycles, handoff/acceptance fingerprints, recommendation/confidence/time/provenance and coverage/staleness. Unknown fields stay unknown. No full card/transcript/source copies; bounded redacted reason templates rather than raw logs. Nerve has no synchronous OpenViking dependency and no code path calling `kanban_complete`, request changes, block, unblock or dispatcher. Supervision advises the authorized orchestrator; it never becomes a second control plane.

## 8. Laya typed sidecar contract, not released support

Canonical source is `NandhaKishorM/laya`, distribution `laya[serve]`, command `laya-serve`, not the archived separate `laya-serve` package. Research release R (`laya==0.3.20`) and newer source S both report 0.3.20 but have materially different behavior. R lacks model revision pinning and bounded serving admission; S supports pin-aware loaders but stock serving does not wire their revision configuration. No qualified published official image is established. **A reviewed pin-aware sidecar bootstrap/Router injection or upstream fix is required; this design does not claim it exists.** Keep torch and model dependencies outside Hermes.

Deployment acceptance must bind package/source, transitive dependency lock, base/sidecar image digest, checkpoint revision and every tokenizer/config/weight artifact hash. Acquire only after approved download/compute scope, use controlled cache paths and verify offline selection. `HF_HUB_OFFLINE=1` alone does not guarantee cache identity. Mount persistence, nonroot ownership, CPU/memory/thread limits and startup behavior require fixture evidence. CPU quickstart guidance (8 GB RAM/10 GB disk) is not a measured RepoKit requirement; GPU is optional and no universal VRAM claim is made.

Use internal `POST /v1/systemone` with a fixed `{state,questions,model}` request and validate `{model,answers,usage,routing}`. Set scoped `LAYA_API_KEY` for inference; do not treat unauthenticated `/health` as authorization, provenance or inference success. Reject unknown checkpoint aliases client-side, since upstream may auto-route; preload configuration is not a serving allowlist. Router selects models only.

Nerve owns one versioned rubric with four questions, never arbitrary caller-supplied prompts/models:

| Question | Type | Meaning |
| --- | --- | --- |
| progress | choice | CONTINUE / WATCH / REPLAN / BLOCK recommendation only |
| evidence | score with exactly two ordered levels | Expected ordinal index in [0,1], not truth probability |
| escalation | noul | P(true) in [0,1], not boolean authority |
| retry | choice | retry-same / retry-after-delay / replan / human-input |

Send bounded sanitized observations/fingerprints, not credentials, raw logs or source. If evidence does not fit the selected model's context, report incomplete/UNKNOWN rather than quietly truncate and claim full assessment. Proposed client limits: one in-flight call, 32 coalesced pending task observations, 16 KiB request/response caps, 1-second connect/10-second total deadline, no redirects, at most one delayed transient retry and 30-second circuit-open cooldown. Qualified server admission must bound ongoing compute too; client timeout does not cancel inference, and must not launch replacement model processes.

Validate exact answer IDs/types/enums, finite probabilities, expected label keys/legend, probability sums within 0.001, score range, selected checkpoint/schema and freshness. Missing/extra/malformed/oversized or stale/provenance-mismatched results fail closed to UNKNOWN. Return `KNOWN` with recommendation, evidence score, escalation probability, retry class, per-answer confidence, evidence-derived reasons, observed time and provenance; otherwise `UNKNOWN` with reason and explicitly stale last-known evidence if useful. Low confidence, outage, missing weights, timeout or incomplete evidence shows advisory WATCH, never fallback BLOCK. Confidence thresholds require calibrated fixtures; do not invent universal accuracy. Laya does not generate free-text reasons or know whether a card should be completed.

## 9. Independent status and failure degradation

Report component verdicts `healthy`, `degraded`, `blocked`, with `unknown/pending` evidence where appropriate; include observation freshness and separate desired alignment. Hermes uptime is neither whole-stack readiness nor proof every component failed. Status never writes a canary, opens a migrating DB, refreshes credentials or invokes a model. Activation readiness probes that mutate or cost money require separate scoped permission.

| Failure/state | Truthful report and bounded behavior |
| --- | --- |
| Hermes stopped/unhealthy | Runtime unavailable; preserve all state and sidecar evidence. Do not create a second Hermes to diagnose. |
| Kanban unavailable/schema mismatch or capability/review policy drift | Block dispatch dependent on the unavailable board or affected policy/execution surface; preserve canonical DB/history. Independent infrastructure/observation can continue; never route work around Kanban with Nerve. |
| Nerve missing/full/stalled/restarting | Observer degraded, coverage gaps visible; native authorized work continues. Drop/coalesce bounded telemetry; read-only reconciliation, no transition replay/model storm. |
| Laya missing model/unhealthy/timeout/malformed/low confidence | Nerve UNKNOWN/WATCH; no automatic block or reroute. Report configured version/checkpoint/backend versus verified/loaded state separately. |
| Native upload incompatible with privacy policy | Block incompatible memory-connected sessions/private processing. Permit eligible provisioning/non-inference observation without triggering uploads; no invented toggle or provider substitution. |
| OpenViking `/health` passes but auth/ready fails | Memory blocked/degraded independently of Hermes. Health is unauthenticated; do not report successful native recall. |
| OpenViking outage/extraction pending | Degraded memory, not a blanket Kanban/engineering-workflow stop: already-authorized work continues using available local context/built-in memory, explicitly lacking shared recall. External recall/write durability is unavailable or uncertain. No provider switch, deletion, fake replication or guaranteed replay. This does not waive native-upload privacy compatibility or authorize uncertain pending uploads. |
| Model/provider budget or consent absent | No affected downloads, inference or data processing. Installation/health cannot spend money or authorize egress. Core functions may remain available, but complete team readiness is not claimed. |
| Superpowers absent/revision/scanner mismatch | Methodology/pin admission blocked; no silent trust bypass or latest upgrade. Full release readiness remains blocked. |
| Sidecar-specific apply failure | Leave unaffected owned services/state intact; record actual partial effect and pending recovery. Resume only from observed identity/version/mounts, not blind replay. |
| Apply interrupted or quiescence unknown | Stop further mutation/dispatch release; preserve transaction/recovery evidence. Never erase state or falsify done to clear a lock. |

Status fields cover Hermes identity/version/mounts; Kanban configuration/concurrency/board; effective fleet descriptions/capabilities; Nerve loaded processes/consumer/backlog/coverage/assessment freshness; Laya artifact/checkpoint/backend/model-load state; OpenViking health/ready/auth/provider/namespace/version; Superpowers exact revision/enablement/scanner evidence. Probe unsupported surfaces as unknown. Detailed secrets, expanded config and raw transcript/tool output never appear in status.

## 10. Immutable apply and native Superpowers admission

Desired `.hermes/repokit/manifest.json` is versioned nonsecret data: canonical repo/project identity, explicit roster target `default|engineering`, selected immutable component artifacts/adapters, layout/network, fleet/descriptions/capability policy, native memory identity references, Kanban mode/concurrency intent, Nerve/rubric version and plugin pins. It is not a credential store, executable adapter path, automatic upgrade selector or blanket authorization to dispatch/process data. Observed `.hermes/repokit/state.json` records bounded evidence and transactions, not an alternate board.

Pin the Hermes image digest, OpenViking image/version, Laya package/checkpoint and supporting artifacts, Superpowers full commit, and both RepoKit plugin trees. `apply` changes these only when the operator explicitly changes desired selections; movement of any upstream `latest`/branch/tag alone produces no upgrade. Apply reconciles explicitly selected desired state, validates preimages/ownership and preserves native sessions/credentials/history, board, local memories, OpenViking data, Nerve history and Laya cache. No-op must preserve artifacts/state without gratuitous restarts. Qualify sidecar-specific replacement/recovery and all migrations. Keep prior known release/configuration identity and consistent backup; old image alone is not safe rollback after a data migration.

Native Superpowers installation uses `obra/superpowers` at an approved full 40-character SHA, through native plugin admission. Safe scan may continue; caution requires exact revision/current findings approval; dangerous refuses. Missing/disabled/failed scanner blocks. No generic force trust bypass, stale caution approval or blanket replacement consent. Verify final installed tree/provenance/enablement, alias-safe discovery and required fresh-session behavior; no promise of post-compaction restoration. A plugin pin or skill cannot grant runtime authority.

## 11. Self-hosting is a release gate

RepoKit must bootstrap the environment that develops RepoKit itself, without circular dependence on agents. These are eventual acceptance requirements, **not current execution permission**:

1. On a clean supported host, clone a known reviewed RepoKit release. Minimal deterministic host tooling verifies documented prerequisites and immutable selections; do not install/enable host Docker, change privileged groups or trust a remote shell script implicitly. No inference, autonomous dispatch or pre-existing RepoKit runtime is needed to bootstrap. Fail clearly for missing prerequisites.
2. Install into that checkout; prove one Hermes/one Compose project, persistent `.hermes`, only native default (zero specialist homes), canonical Kanban with dispatch/auto-decompose disabled, admitted non-autonomous internal OpenViking/Laya, loaded Nerve and exact enabled Superpowers. Pending private gates remain explicit, not fake health. Independently qualify the sidecars before claiming complete stack readiness.
3. Through private setup, authorize providers/keys, permitted fixture data, disclosure/compute budgets and any approved product compromise; engineers qualify the execution/review surfaces used by that fixture. Then activate eligible components without roster expansion and explicitly choose managed concurrency 1: provision the engineering roster with claims suspended, verify all five native profiles and effective capabilities, and only then release the qualified task. No credentials or real inference are inferred from install/health success.
4. Give the installed team one **real bounded change-bearing card**, for example improving `hermes-repokit status`, with research/planner handoff only where useful, bounded builder changes/tests and independent reviewer evidence before done. The builder/reviewer stay on the same change card; planning can be a handoff or a meaningful dependency. Record actual native identities/runs, candidate revision, acceptance evidence and review decision; simulate neither model-backed work nor approval. Changes requested return to the same builder/card and require fresh independent review.
5. Host operator suspends every native claim entry point and drains/verifies workers, interactive writers, gateways, setup sessions, session finalization/extraction and Nerve producers/consumer as required for the affected state. A lock or empty queue alone is insufficient. Do not kill away task history, erase state or mark cards done to manufacture quiescence. Active/unknown writers block disruptive apply.
6. The operator reviews and explicitly selects the improved candidate checkout/revision. Publish the reviewed CLI in a host-controlled immutable versioned location, recheck its content digest/revision immediately before execution, and invoke that candidate directly rather than a mutable PATH selector or partially edited worktree script. Invoking edited host code is arbitrary code execution requiring approval. Publish/select the verified candidate atomically with the previous known executable/recovery path retained. Builders may change approved source worktrees, but cannot mutate runtime selectors/manifests/credential stores or run self-recreation. The supported execution surfaces in §3 must demonstrate those protections; the bounded threat model does not waive them.
7. Apply preserves single-Hermes identity, project/mount identity and all state; dispatch remains suspended until the operator explicitly re-enables managed mode after gates pass. Verify source changes, native Kanban history, OpenViking knowledge, sessions/auth integrity without disclosure, built-in memories, Nerve history and Laya cache survive restart/reconciliation. Compare unchanged credential bytes/permissions privately with boolean-only results (no published secret hashes); verify sessions are addressable and DB history through consistent logical records rather than unstable live-file hashes. Knowledge persistence needs an authorized actual write/recall fixture, not merely a surviving directory. Test interrupted self-apply and recovery without unsafe migration rollback claims.

**Pi-free release gate:** run the complete clean-host workflow above from a fresh `hermes-repokit` clone on an authorized disposable machine where Pi and its packages/resources are absent (or inaccessible to every process). User tests, generated runtime configuration, installed Hermes actors and host self-apply must succeed without Pi. Checking only `which pi` is insufficient: inspect dependency/artifact closure, forbid subprocess/import/service access, and retain bounded evidence of the actual workflow. Never uninstall Pi from the developer's machine to run this test. Development planning documents may mention Pi; released execution paths may not depend on it.

**Three evidence levels:**

- **Offline/default:** pure configuration/policy/schema tests, fake Docker/process/provider fixtures, queue bounds/deduplication, typed response failures, capability denial, scanner/lock/crash models and nonmutating status. No Docker, model download, inference or credentials. These prove local contracts only.
- **Opt-in real runtime:** qualified immutable stack on disposable owned hosts/repos, real mounts/profiles/Kanban/plugin/sidecar startup, identities, non-inference health/auth checks, persistence/outage/recreate/upgrade/no-op/interruption fixtures. Use authorized nonsecret fixtures/stubs where needed and label them. Writable DB probes are mutating readiness tests, not status. No implication of successful real models or calibrated decisions.
- **Opt-in real inference/self-hosting:** explicitly scoped providers, budgets, data, model downloads/compute and cleanup authority. Actual team task/review, Laya typed workload/calibration, shared-profile memory and negative cross-repo isolation, extraction/recall/persistence and reviewed host self-apply. Only this level can satisfy the full self-hosting release gate. No secret-bearing logs or external notifications without separate authority.

Every inference fixture needs enforceable ceilings for runs/correction cycles, wall time, aggregate tokens/external spend (including OpenViking embedding/extraction), local compute and downloads. No ceiling is approved by this document, and Hermes exposes no extraction spend cap. If the selected scope cannot be bounded, leave the fixture blocked; on exhaustion suspend claims and report incomplete without manufacturing completion. Notifications remain off unless explicitly authorized. Synthetic-canary offline instrumentation must check sanitized output/payload contracts without claiming generic secret filtering of native transcripts.

Eventual opt-in E2E CI follows clean host → install → private/nonsecret fixture setup → activate → managed → real task/tests/review → quiescent host apply → state survives. It cannot run by default, use unspecified paid providers or treat stub pass results as real-inference evidence.
